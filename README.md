# ScanLab

EviLog 扫码速度的**实验包**，与正式 App 完全无关，不引用它的任何代码。

测的问题只有一个：**先把面单框出来、提前换镜头/推近，能不能让「第一次读到单号」变快。**

## 出包 / 装机

Actions 页面手动 Run `ScanLab .ipa` → 从 [Releases/scanlab](https://github.com/VidLog0705/ScanLab/releases/tag/scanlab) 下 `.ipa` → Sideloadly 装上。
Bundle ID 是 `com.evilog.scanlab`，与正式 EviLog 可以同时装在一台手机上。

## 用法

```
  ○ 连续   ○ 裁框   ● 绿框   ● 对焦   ● 预缩   ● 选镜

  [ 导出 3 ] [ 清零 ]        ┌──────────┐
                             │ 本件开始  │
                             └──────────┘
```

## 连续扫码模式（0.1.7 起）

拨开【连续】= **不用再按【本件开始】**，自动一件接一件：

```
① 面单进框（Vision 矩形）
② 按「面单长边 ÷ 取景框边长」反算倍率，瞬时推近（封顶 = 传感器长边 ÷ 视频长边）
③ 读到 → 记一条（= 正式端「上水印 + 开始录制」那一步）
④ 保持 2 秒
⑤ 缓退回原倍率（1 倍/秒）
⑥ 等这件离开（0.75 秒看不见）→ 回到 ①
```

为什么是 **占比 0.65** 而不是固定倍数：目标是把面单推到占取景框 65%。
50cm 只要 1.07x（不用推）、70cm 1.49x、80cm 1.70x、100cm 2.13x（正好压在上限 2.1）。
**这是唯一一条能同时覆盖 50~100cm 的规则**，因为它读的是「现在多大」而不是「猜多远」。

**推近发生在读到之前**（正式端是读到之后才推，那是确认动作，不是搜索动作）。
所以推近可以**瞬时**完成 —— 它不在视频里，没有缓动的必要；只有**退回去**要缓，因为退的过程录进了画面。

HUD 上多的那一行就是判据：

```
连续 推近读  占比 0.31  推 1.70x  上限 2.10x
```

- `占比 < 0.56` —— 推得不够，或者矩形框住的是整个包裹（框太小看绿框）
- `占比 > 0.85` —— 快出框了，镜头上限或者取景框该调
- `⚠️ 推到顶` —— 需要 2.10x 以上，再推只是插值，不增加信息。**这一件只能靠走近或者换更高的视频档**

开关冲突：【连续】打开时【预缩】【选镜】自动让位（两套变焦逻辑同时跑，倍率是谁改的就查不出来了）。CSV 的「开关组合」列会照实写。

### 0.1.8 修的三条（2026-11-09 真机数据逼出来的）

1. **一个静止的包裹被记了 5 条** → 重臂原来只看「面单框消失 0.75 秒」，而矩形检测在静止面单上会抖。现在用**单号**当身份：号码变了才算换了一件；同一件必须框和码都静默 2 秒才重新武装。
2. **`读到占比` 记的是冻结的旧值** → 读到那一帧如果没检出矩形，这个格子现在**留空**。空 = 量不到，0 = 量到 0，别混。
3. **单号乱码照样收**（实测读出过 `JT5,($VfF`）→ 现在只认 `A-Z0-9-`、长度 10–24 的串，不合格式的被丢弃并在屏幕上打红字「丢弃不合格式：…」。**这条正式端没有**，是拿来测「挡得住吗」的。

【导出】上直接写着件数；**没数据时它是灰的**（灰 = 点不动，不是坏了）。

一件 = 按【本件开始】→ 面单放进白框 → 读到 → 屏幕出单号、耗时、失败轮数。

右上角那个小窗 = **送进识码器的那张图**（每 0.5 秒一张）。读不到码时先看它：

- 图是正的、面单占满了 → 图没问题，往下查分辨率/对焦
- 图是歪的、只有一角、或者黑的 → 相机的方向/裁剪错了，跟分辨率无关
- 图明明很清楚还是读不到 → 看有没有 `⚠️ 识码抛错` 那一行

顶部小字是判断依据，不是装饰：**「面单」那行长期是 `—` 就说明矩形检测没抓到面单**，绿框/对焦/预缩放/选镜头全都没有输入，那几组数据等于没做。

「条码」那行是识码器这一次的**原始观察**：

- `0 个` —— 一张码都没看见（不是「看见了但读不出」）
- `Code128` —— 看见了、正文也解出来了
- `ITF14无正文` —— 看见条码图案但解不出内容，是码制或清晰度问题

⚠️ 这个包**故意放宽了码制**（`code128/code39/code93/itf14/ean13`），正式端只开 `code128`。放宽只是为了问出「是不是码制不对」；读数时以那行为准。

下面那行「矩形」是候选清单，格式 `面积/长宽比`：

- `矩形 0 个` —— Vision 一个矩形都没检出来，先别测，换角度/换光再试
- 列了一串但绿框还是套在包裹上 —— 说明面单的矩形没进候选，把这一行截图发出来
- `→ ` 后面那个就是被选中的，判断规则：**长宽比 1.15–2.6 且面积 ≤ 55%** 的里面挑面积最大的；一个都不符合才退回挑面积最大的

## 怎么测得准

采集分辨率**必须和正式端同一档**（正式端默认 1080P，这个包原来开的是 720P，像素密度只有 1/2.25 —— 真机上就是「一个字都读不出来」）。屏幕第一行 `送帧 W×H` 里能看实际尺寸。

同一台机器，两组开关**交替**做（A/B/A/B），不要一组做完再做另一组 —— 后面那组会被热降频拖慢，能把结论做反。

- 组 A：`裁框`开，其余全关 = 现在的做法
- 组 B：全开 = 设想的做法

各 20 件，【导出】拿到 CSV。连续扫那组直接放着扫 20 件就行；多出来的四列是
`推前倍率 / 推前占比 / 读到占比 / 推到顶`，**判「该推多少」就看这四列**。

⚠️ 这个包**没有录制负载**，绝对耗时一定比正式 App 快。只有同机不同开关组合之间的**相对**差异有意义。

## 代码在哪

| 文件 | 干什么 |
|---|---|
| `Sources/ScanEngine.swift` | 采集会话、Vision 识别、面单检测、对焦、变焦、选镜头、计时 |
| `Sources/LensMath.swift` | 纯算式：倍率换算、屏幕⇄设备坐标、距离估计、镜头分界（含自检，结果打红字上屏） |
| `Sources/ScanViewController.swift` | 界面与开关 |
| `Sources/Metrics.swift` | 记录与 CSV |

- 「预缩」不再是固定倍数，而是**把面单推到占画面一半**（`preZoomTargetFill = 0.5`，上限 4x，推近用 3 倍/秒）。依据是真机量到的：80cm、1x 时面单只占 14%，条码只剩 ~100 像素，而 Code 128 稳定解要 ≥160 像素 —— 固定乘 1.6 只推到 160，等于没推。倍率会写进 CSV，**看读到时的倍率就知道这个距离到底要推多少**。
- 距离分界 `LensMath.closeLimitMeters = 0.32`：32cm 内换 0.5x 超广角。依据是 15/16 Pro 主摄最近合焦约 20cm，小于这个距离怎么对焦都是糊的。真机测不对就改这个常量。
- 焦点十字是故意画出来的：对焦点在屏幕⇄设备之间的换算若有错，十字就会跑到别处。**十字不落在面单中心 = 换算错了**，把【对焦】关掉即可把这一项从实验里摘出去。
